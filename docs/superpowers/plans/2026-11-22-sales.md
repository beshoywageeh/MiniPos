# Sales Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the sample new-sale screen into a working sale entry flow: a tested document-number generator (the still-unimplemented half of the document-sequences plan), a Livewire 4 create-sale page that persists `Sale` + `SaleItem` snapshots, writes `StockMovement` OUT rows, records the matching `Payment`, and replaces the mockup.

**Architecture:** `App\Support\DocumentNumber` formats and increments a `document_sequences` row inside a `lockForUpdate` transaction (per `docs/superpowers/plans/2026-11-20-document-sequences.md` Task 1; the management UI stays a separate plan). One full-page Livewire SFC (`livewire.sales.create`) holds all form state server-side: party, warehouse, dates, line items with a server-side product search backed by the same matching rules as `ProductLookupController`, totals, and payment. Saving runs in a DB transaction: number the sale, create items with product snapshots, derive status from paid amount, write stock movements and a receipt payment only for non-drafts.

**Tech Stack:** Laravel 13, PHP 8.5, Livewire 4.4 SFC, Pest 5, Blade components (`x-card`, `x-table`, `x-modal`, `x-form.*`, `x-button`, `x-badge`, `x-page-header`), SQLite (dev and tests).

**Spec:** `docs/superpowers/specs/2026-11-20-products-settings-document-sequences-design.md` (section C) plus the existing seeded-sale conventions in `DemoDataSeeder`.

## Global Constraints

- Routes use `Route::livewire()` inside the existing `['middleware' => ['auth']]` group in `routes/web.php`.
- Always pass `--no-interaction` to Artisan commands.
- Document numbers are `prefix-` + `str_pad(next_number, padding, '0', STR_PAD_LEFT)`; a missing sequence throws `RuntimeException("No document sequence configured for [type].")`; no fallback.
- Reset boundaries use the application timezone (`now()`).
- Sale status derivation mirrors `DemoDataSeeder::paidScenario`: draft → `DRAFT`, paid ≥ total → `PAID`, 0 < paid < total → `PARTIAL`, paid = 0 → `PENDING`.
- Draft sales get no stock movements and no payment (seeder convention).
- Sale payments are `PaymentType::recipt`, dated on the invoice date, `party_id` = the sale's party, and require a cashbox.
- `SaleItem` snapshots `product_name`, `sku`, `cost_price` (product `purchase_price`), and computes `line_total` server-side; never trust client totals.
- Stock movements use `reference_type = Sale::class`, `reference_id = $sale->id`, `movement_type = OUT`, `unit_cost` = the item's cost snapshot.
- Keep the existing `sales.invoice_preview` route and view untouched.
- After changing PHP, run `vendor/bin/pint <paths> --format agent`.
- Narrow test command: `vendor/bin/pest tests/Feature/DocumentNumberTest.php tests/Feature/SalesCreateTest.php --compact`.

## Review Focus

- `DocumentSequence::last_reset_at` must be cast to `datetime`; without it the Carbon comparisons (`isSameDay`, `isSameWeek`, …) receive a string and break.
- The first call for a sequence whose `last_reset_at` is `null` resets `next_number` to 1 and stamps the timestamp (spec rule; preserves `DatabaseSeedingTest`'s `count + 1` assertion).
- `Sale::$fillable` omits `document_number`, so `Sale::create()` silently drops it; fixed in Task 2.
- The product search inside the create component must reuse the lookup matching rules (barcode → sku → code → name, active only, exact barcode first) so the standalone endpoint and the form can never drift; extract the matcher rather than duplicating it.
- Totals are computed server-side from item state; the client sends only quantities, prices, discounts and tax rates.
- `due_date` is nullable but must be `after_or_equal` the invoice date when present; paid-in-full sales may leave it empty (seeder convention).
- The `payments.cashbox_id` column is required, so the cashbox select is required whenever `paid_amount > 0` and hidden for drafts.
